# AI extraction and bulletins — implementation notes

Reference notes for phase 4, keyed to *Aegis — Technical Specification v1.0*.

Phase 4 is done when there is a "privacy-safe auto/review bulletin pipeline"
(§14). `tests/integration/test_bulletin_pipeline.py::TestPrivacy` is the
privacy half of that criterion, and `TestRoutingInPractice` is the routing
half.

## 1. The AI data boundary is enforced twice

§8.1: "The model never receives client-identifying data." That is a property
worth more than one mechanism, because a leak is a client's hostnames
leaving their boundary and no amount of care afterwards repairs it.

**Structurally.** Everything sent to a model is a `PublicPayload`, and the
only constructors of one take an `intel_record` or a fetched public page.
`bulletins/drafting.py` imports nothing tenant-scoped;
`bulletins/templates.py`, which handles every client field, imports no model
client. The ordinary way of writing this code cannot leak.

**At runtime.** `PrivacyGuard` scans the assembled payload before the
request and raises `PrivacyViolation` on a tenant slug, name, hostname or
address — plus RFC1918 literals and `.internal`/`.corp`/`.local` names,
which are client topology whoever they belong to. The structural rule
already prevents today's mistake; this catches the refactor that
reintroduces it later.

There is deliberately **no scrub function**. Redacting a payload that should
never have contained client data hides the bug that produced it. The only
correct response to a violation is to fix the caller, and `PrivacyGuard.scrub`
raises `NotImplementedError` saying so.

## 2. Prompt-injection hardening (§8.3)

Advisory pages are fetched from the public web and are therefore hostile
input. Three defences:

* Page text is wrapped between `<<<UNTRUSTED_PAGE_CONTENT` markers, and any
  occurrence of those markers *inside* the page is neutralised — otherwise a
  page could close the block early and have its remainder read as
  instructions.
* The system prompt states the markers delimit data, that instructions found
  inside must never be followed, and that a page attempting it should be
  reported in `reviewer_note` while normal extraction continues.
* The output is a strict schema. A model that followed an injected
  instruction still cannot return a field shape Aegis does not accept, and
  cannot return a CVE id at all.

## 3. The model is never asked for a CVE id

§4.2: "CVE IDs are never generated by the model." Rather than validating one
after the fact, `AdvisoryExtraction` has no `cve_id` field. The pipeline
knows which CVE it fetched a page for and supplies it. `extra="forbid"`
means a model that volunteers one fails validation.

Every claim field is optional, too. A model that cannot find a fact returns
nothing for it, which is the honest answer; a required field invites a guess.

## 4. The two-source rule (§4.2)

> Each material claim requires >=2 independent sources, or it is marked
> low-confidence and queued for human review. Unsourced claims are discarded.

| Citations backing a claim | Result |
| --- | --- |
| none | the claim is **removed** from the extraction |
| one, high-stakes field | confidence forced to low, queued for review |
| one, other field | confidence capped at medium |
| two independent publishers | kept as stated |

"Independent" means different **publishers**, not different URLs: a vendor
advisory and its own mirror are one source, judged by registrable domain.
That is an approximation of a public suffix list — enough to stop the common
case of one page cited twice, and documented as such.

`exploit_status` and `vendor_confirmed` are the high-stakes fields, because
§7.2 treats vendor confirmation as KEV-equivalent and it drives out-of-hours
escalation. A single source is never enough for those.

A citation with no quote counts for nothing. §4.2 requires a supporting
quote, and a bare URL is an assertion that something somewhere says so.

## 5. Drafting and template injection (§8.1)

```
draft   = llm(public_intel_view)        # CVE facts only
bulletin = render(template, draft, hostname=..., exposure=..., tier=...)
```

The draft is **cached per CVE within a run**: ten hosts running the same
vulnerable FortiOS share one public draft. That is a cost decision and a
consistency one — ten clients reading ten slightly different explanations of
the same CVE is worse than ten reading the same one.

`bulletin.draft_body` keeps the public half separately from the rendered
`body`. That is the audit evidence for §8.1: it is exactly what the model
produced, and a reviewer can confirm no client field appears in it.

**Without a model, bulletins are still issued.** `draft_public_prose` falls
back to a deterministic summary of the same facts when the LLM is disabled,
unreachable, or returns nothing. A finding nobody is told about is worse
than plainer prose. `Bulletin.drafted_by` records which it was.

`Draft.is_model_written` is a field, not derived from `Draft.model`: whether
a model wrote the text and whether the caller recorded *which* model are
different facts. Deriving one from the other made an unnamed model draft
look like a failed one, which then blocked auto-issue under §8.2.

## 6. Automation tiers (§8.2)

| Condition | Outcome |
| --- | --- |
| Exploited + patch available + exposure verified | auto-issued, logged |
| Conflicting intel / no patch / unverified exposure | queued for analyst |
| Critical on crown-jewel asset | mandatory review |

Two things about the order. **Row 3 overrides row 1**: a Critical finding on
a crown-jewel asset satisfies row one's conditions and §8.2 still sends it to
a human, so `mandatory_review` is evaluated first and cannot be waived.

And "under tenant policy" is honoured literally: a tenant whose
`automation_policy` is `review_all` has nothing auto-issued, regardless of
how safe the platform judges it. The platform's confidence does not override
the client's decision.

"Conflicting intel" is detected concretely: two sources asserting different
values for the same *exploitation* field. Sources differing on a CVSS score
is routine; one saying a CVE is exploited while another says it is not is
exactly what §8.2 sends to an analyst.

Every review reason is collected rather than short-circuiting on the first,
because an analyst picking up the queue should see the whole picture.

## 7. Model configuration (§8.3)

`llm_provider` is `anthropic` or `self_hosted`; the latter points
`llm_base_url` at an Anthropic-compatible endpoint, which is the second
deployment §8.3 allows. Default model `claude-opus-5-5`.

`llm_require_zero_retention` (on by default) refuses to run against the
hosted API without an explicit `llm_api_key`: a missing key means the SDK
resolves ambient credentials, which may belong to a retaining account, and
§8.3 wants that choice made deliberately.

## 8. Not built in this phase

* **Ticketing, alerting and the portal** (§12) — phase 5. Bulletins are
  produced and stored; delivering them is next.
* **RBAC/SSO and the audit log surface** (§11) — phase 5. The underlying
  append-only rows exist (`feed_run`, `match_run`, `score_run`,
  `verification`, `bulletin`).
* **A human review UI.** `aegis bulletin issue --analyst` records the
  decision from the CLI; the queue has no interface yet.
* **PSIRT advisory discovery.** The pipeline reads vendor advisory URLs NVD
  already published. Nothing is found by browsing.
